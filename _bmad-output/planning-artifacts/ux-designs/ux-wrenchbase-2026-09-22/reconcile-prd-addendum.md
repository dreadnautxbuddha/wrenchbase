# Reconciliation: Wrenchbase PRD Addendum

## Reconciliation verdict

The addendum is a retained focused contract, delivery, and implementation
document. It is not replaced by the UX spines. UX-visible consequences migrate
to `EXPERIENCE.md`; the addendum's protocol, persistence, delivery sequencing,
and engineering-verification details remain here and in the focused technical
documents that control their own subjects. The addendum establishes no visual
direction, so it contributes no independent requirements to `DESIGN.md`.

The canonical PRD remains authoritative for product behavior and milestone
boundaries. All supplied sources remain retained through the UX approval
checkpoint.

## Exact UX migration summary

### Migrate to `EXPERIENCE.md`

- API authority for rules, authorization, validation, persistence, and
  authoritative completion, with client-owned presentation and interaction.
- Provider-neutral authentication behavior and session-safe recovery without
  exposing implementation-provider details.
- Explicit Workspace context, Capability-driven controls, tenant concealment,
  and atomic user-visible outcomes.
- Applicability-based loading, empty, Unauthorized, Not found, validation,
  network, conflict, stale-revision, and missing-precondition states.
- Retry-safe creation and command behavior; clients use returned read models
  rather than predicting normalized state.
- Global input preservation after validation, network, semantic-conflict, and
  stale-version failures.
- Keyboard-, touch-, and assistive-technology-operable tree actions, with an
  explicit alternative to drag-and-drop.
- Consequence previews before publication, movement, Installation, detachment,
  Reconciliation, and lifecycle changes.
- The MVP 0 and MVP 1 golden-path inventories as milestone-scoped validation
  evidence, without inventing missing routes or screens.

### Migrate to `DESIGN.md`

The addendum creates no independent visual direction. `DESIGN.md` only needs to
support the migrated behavioral contract through visible focus, non-color-only
state communication, readable retained-input and conflict treatments, and
accessible presentation of explicit tree actions. Exact tokens and component
appearance must come from the approved visual-design source, not this addendum.

### Retain outside the UX spines

Retain protocol versions, endpoint paths, media types, identifiers, cursor
ordering and sizes, HTTP mechanics, ETag and idempotency storage details,
database roles and row-level security, transactional implementation, delivery
workers, engineering sequencing, repository checks, test infrastructure, and
extraction-record filenames in their focused documents.

## Unresolved conflicts and open questions

- **UX-OQ-2 — MVP 0 settings boundary.** The addendum's MVP 0
  `GET/PATCH /workspaces/{workspaceId}` contract and stale-edit golden path
  support basic Workspace editing in MVP 0, while the canonical PRD milestone
  summary names settings under MVP 1. The UX artifacts must not silently choose
  a milestone interpretation.
- **UX-OQ-6 — missing-precondition recovery.** The addendum distinguishes HTTP
  `428` from `412`, `409`, and validation failure but does not define its
  user-facing recovery.
- Authenticated server rendering and bearer-token cookies remain an explicit
  architecture decision. No UX behavior is predicated on either approach.

## Dropped-detail audit

No qualitative UX requirement is intentionally dropped. Details excluded from
the UX spines are protocol, storage, database, delivery, sequencing, testing,
or provenance facts retained in the addendum and the focused documents it
references. MVP 1 facts remain retained and milestone-deferred where the
sources do not yet define a screen, route, or interaction.
